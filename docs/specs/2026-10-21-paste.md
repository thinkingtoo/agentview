# Paste: text that waits on the page until the person uses it

**Status:** ready-for-agent
**Date:** 2026-10-21
**Origin:** grilling with Thierry in a tiroir session (Q1–Q12, all settled)

## Problem Statement

Sessions hand the person text to paste elsewhere: a mail draft for a colleague, a policy file
for a web console, a command for another terminal. Today a session puts that text on the system
clipboard. The clipboard is one slot shared by every session on the machine, so with several
sessions running, whatever is there belongs to whichever session wrote last. On 2026-10-21 a
message for Sven was overwritten twice in an hour by a Tailscale policy file from the same
session, and the person could no longer tell what his clipboard held. A text handed over is
only useful if it is still there, unchanged, when he gets to it.

## Solution

A session leaves the text on the page as a **Paste**: a titled piece of text attached to that
session's card. It waits there with a copy button and a done button until the person ticks it
done, or until the session withdraws it because it saw the thing happen. Copying never removes
it. Several Pastes can wait on one session. A Paste that holds a secret goes into the person's
login keyring instead of a file, and the page shows it masked. Sessions stop touching the
clipboard unless the person asks for it in so many words.

## User Stories

1. As the person, I want a text a session hands me to stay on that session's card, so that another session cannot overwrite it.
2. As the person, I want each Paste to have a short title, so that I can tell "Message to Sven" from "Policy without central" at a glance.
3. As the person, I want to see the first line of a Paste on the card, so that I recognise it without opening it.
4. As the person, I want to open a Paste and read the full text, so that I can check it before I use it.
5. As the person, I want a copy button that copies the exact text, every character and line break, so that what I paste is what the session wrote.
6. As the person, I want the button to say it copied (or that it could not), so that I know the clipboard now holds this Paste.
7. As the person, I want copying to leave the Paste in place, so that I can copy again if I got distracted before pasting.
8. As the person, I want a done button on each Paste, so that I decide when it is finished.
9. As the person, I want several Pastes on one session at once, so that a session can hand me a policy file and a message in the same turn.
10. As the person, I want a count of waiting Pastes in the page header that takes me to the first one, so that I never miss one on a card I have scrolled past.
11. As the person, I want a Paste to stay after its session has finished or been closed, so that closing a session never throws away a message I still have to send.
12. As the person, I want a Paste to count among the things waiting for me on that session, so that the number on the card is honest.
13. As the person, I want no new sound for a Paste, so that the chime keeps meaning "a session is blocked on a question".
14. As the person, I want a Paste that holds a password, token or API key kept in my login keyring, never in a plain file, so that a secret does not sit readable on disk.
15. As the person, I want a secret Paste shown as dots with a working copy button, so that a screen share or a glance over my shoulder does not reveal it.
16. As the person, I want a secret Paste deleted from the keyring when I tick it done, so that secrets do not pile up there.
17. As the person, I want a secret recognised and stored in the keyring even when the session forgot to mark it, so that one careless session cannot leave a token in a file.
18. As the person, I want sessions to stop writing to my clipboard unless I ask, so that my clipboard holds only what I put there.
19. As the person, I want to still be able to say "put it on my clipboard" and have it done, so that the old way stays available when I want it.
20. As a session, I want one command to leave a Paste, reading the text from a file, so that quotes, backslashes and line breaks never break on the shell.
21. As a session, I want the command to print the Paste's id, so that I can withdraw it later.
22. As a session, I want to withdraw a Paste by id when I have measured that it was used (the mail is sent, the policy is live), so that the person is not asked to tick off what is already done.
23. As a session, I want a clear error when the file is missing, empty or too large, so that I never report a Paste that does not exist.
24. As a session, I want to mark a Paste secret explicitly, so that I do not rely on the detector alone.
25. As a session, I want the command to fail loudly, not silently fall back to a plain file, when a secret cannot reach the keyring, so that a secret is never written in the clear.
26. As a new session, I want the reminder I already get for the session line to name the Paste command, so that I use it instead of the clipboard from habit.
27. As someone reading the code later, I want **Paste** in the glossary, so that the word means one thing across the page, the command and the docs.

## Implementation Decisions

- **New domain term, Paste** (glossary entry): a titled text a session leaves for the person on its card, waiting until the person ticks it done or the session withdraws it. Avoid: draft, clipboard item, handout.
- **A new store beside the session lines**, under the same state directory the lines already use (never under `~/.claude`, which is committed nightly, nor anything brain-sync carries). One record per Paste: id, session id, title, created at, whether it is secret, whether it was copied, and either the text or a keyring reference. Writes are atomic, as the session lines are.
- **A Paste outlives its session.** Pruning of finished sessions must not remove Pastes; only done or withdrawn ones go. A Paste whose session is gone stays visible under that session's finished card.
- **Secrets.** A Paste is secret when the session says so, or when the text matches the secret patterns the project already redacts with. A secret's text goes to the login keyring via the freedesktop Secret Service (the keyring is unlocked at login), and the record keeps only the reference. Done or withdrawn deletes the keyring item. If the keyring cannot be reached, the command refuses and exits non-zero; there is no plain-file fallback for a secret.
- **The command**, next to `team-line` in the hooks folder: create (session id, title, path of a text file, optional secret flag, prints the new id), withdraw (session id, Paste id). Text comes only from a file, never from an argument. A size cap keeps a runaway file off the page.
- **The roster** gains a list of Pastes per session: id, title, first line, secret flag, copied flag. Full text is never in the roster; it is fetched per Paste when the person opens or copies it, so a secret only leaves the keyring on a click.
- **Server routes**: fetch one Paste's text (from the file or the keyring), mark copied, mark done. Same local-only server, same handling of bad input as the existing routes.
- **The page**: Pastes sit on the card under the ask line, as title + first line + copy + done; clicking the title opens the full text. Secret text shows as dots, and opening it does not unmask it. A header count of waiting Pastes jumps to the first. No new sound: the announce logic does not change.
- **Count**: a Paste is one of the things waiting for the person. The session counts it in its own `n` when it writes its line; the page does not add Pastes to `n` a second time.
- **Habit change** (outside this repo, done in the same delivery): the global CLAUDE.md "Clipboard (Proactive Copy)" section is replaced with "leave a Paste; use the clipboard only when the person asks", and the reminder sessions get for `team-line` names the Paste command.

## Testing Decisions

- Test only what the person and a session can observe: what the command prints and returns, what `/api/roster` and the new routes return, and what the page shows. Never the record layout on disk.
- **Command + roster seam**, in the style of the existing route tests: a fake provider behind the roster, a throwaway store, a temp state directory. Cases: create then see it in the roster; several on one session; copy marks copied and keeps it; done removes it; withdraw removes it; a finished session keeps its Pastes; text with quotes, backslashes, tabs and blank lines comes back byte-identical; missing, empty and oversized files are refused.
- **Secrets** through the same seam with a fake keyring that records calls: a marked secret and an unmarked token both land in the fake keyring and never in the store directory (assert by scanning the directory's bytes); done deletes the keyring item; an unreachable keyring makes the command fail and leaves nothing on disk. No test ever touches the real keyring.
- **Page** through the existing UI smoke test: a Paste renders on its card with title and first line, the copy button copies the full text, a secret is masked, the header count matches.
- Prior art: the notes and finished-route tests (route seam with fakes), the lines tests (atomic store), the guessed-command tests (copy button), the UI smoke test.

## Out of Scope

- Sending anything on the person's behalf. A Paste is text for him to use; the session never sends it.
- Syncing Pastes to other machines or to the phone.
- Editing a Paste on the page.
- Disk encryption for the laptop (raised in the grilling as the bigger exposure, a separate decision).
- Other agents' clipboards and the Codex provider's habits, beyond what reading the same command gives them.

## Further Notes

- Why a file and not an argument: shell quoting broke text before, and a single quote in a message is common in Dutch and English alike.
- Why copying does not remove: the person often copies, gets interrupted, and needs it again; done is his call.
- Why the keyring and not encryption with a key on disk: a key beside the ciphertext, readable by the same user, protects nothing against the processes that can read the file. The login keyring is unlocked by his login password, which is the key kept elsewhere.
