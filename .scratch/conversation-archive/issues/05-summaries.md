# 05: Two-line summaries under each result

**What to build:** each search result carries a two-line summary: what the conversation was about, and where it stood when it stopped (done, waiting on the user, half-way). That way you can tell which of several similar conversations is the one to reopen. Spec: `docs/specs/2026-09-29-conversation-archive.md` (decisions table and measured facts).

**Blocked by:** 02: Keyword search across all interactive conversations

**Status:** resolved

- [x] Summaries are written by `claude -p --model haiku` through the CLI, not the API.
- [x] These runs execute with hooks off, so they never appear as sessions on the page and never write team lines. Verified by watching the page during a run.
- [x] A conversation is summarised again once it has been quiet for 10 minutes and has changed since its last summary.
- [x] The backfill of ~525 conversations is paced (a limited number per run) so it does not eat the plan's quota in one go; the pace is written down.
- [x] The summary runs are `sdk-cli` transcripts, so they are left out of the index (02) and deleted after 30 days (01).
- [x] Summaries are stored in the index file and shown in the result row. A conversation that has no summary yet shows only its title.

## Comments

**Closing note (Lucas, 2026-09-29).** Built on `feat/05-summaries`. The code is in `archive.py` (the `summaries` table, `summarize`, `ask_model`, the queue), `providers/claude.py` and `log.py` (a summary run is not a session), the summary lines in `index.html`, `agentview-summaries.{service,timer}`, and `tests/test_summaries.py`. No schema bump: `summaries` is a new table, and unlike the rest of the index it is kept when the index is rebuilt, because each one costs a model call. The real example, the real numbers behind it and the spot check are in `~/.claude/pm/evidence/05.md`, outside the repo, because they carry real conversation titles and summaries.

1. **The CLI, not the API.** `claude -p --model haiku` with `--safe-mode`, `--tools ""`, the conversation on stdin (never on the command line), and `ANTHROPIC_API_KEY` taken out of the environment, so a key in the shell cannot turn it into a paid call (`Asking`, nine tests on the exact command, the environment and what a failure may say). 39 real calls were made through it.
2. **Hooks off, never on the page.** `--safe-mode` is what turns the hooks off: a hooks-on headless run left a team-line record in the events log, a safe-mode run left none. It was not enough for the page, though: a run writes a peer file and the page listed it under *No project* while it ran. So a run works in `~/.claude/agentview/summaries` and a headless session there is ignored by the page and by the log (`OffThePage`, three tests). Watched on a second server during 4 real runs: 940 polls, none showed it; the same watcher on a look-alike directory saw it (374 polls, 1 seen).
3. **Again after 10 quiet minutes and a change.** Quiet is judged on the transcript on disk, not on what the index remembers of it. "Changed" is what the model would be shown, hashed: a transcript that grew by tool output costs no call (`Choosing`, nine tests). A summary is stored only if the conversation is still as it was when the model was asked; one that changed meanwhile is dropped and asked again (`Overlapping`).
4. **Paced.** At most 12 a run, one run every 10 minutes: about 510 conversations in 43 runs, about 7 hours. Measured over 39 real calls: 3.3 s a call, so about 28 minutes of model time in all, and about a cent a call at list price. Thinking is off (`MAX_THINKING_TOKENS=0`): on, Haiku spent 1,700 to 3,800 tokens thinking about a two-line answer and a call took 10 to 50 s. Three failures in a row end a run, and a conversation that fails three times for the same text is left alone. The pace is in the README (`### Summaries`) and in `PER_RUN`.
5. **Their transcripts.** Each run leaves an `sdk-cli` transcript in a folder of its own. The index skips it and `retention.py` (ticket 01) deletes it after 30 days: `TheirTranscripts` runs both over a transcript in the shape a run leaves. On this machine 57 of them from the test runs are on disk, and the retention job's dry run with the clock 31 days ahead names all 57, and none with the clock 29 days ahead.
6. **Stored in the index, shown in the row.** A row shows the two lines under its title, one line each, dimmed with a tooltip when the conversation has moved on since; a conversation with no summary shows only its title, and so does one from an index built before the table existed (`Making`, `BeforeTheFirstRun`, `Endpoint`, `FoundByMeaning`). Rendered on a second server from the worktree, on the merged page: 30 rows, 7 with two lines each. Rebuilding a scratch index from schema 3 to 4 on real data kept all 45 summaries and asked for none again.

**Objective: a finished conversation shows what it was about and where it ended.** Yes, on real conversations; one example and a spot check of four (three match, one arguable) are in the private evidence. The model sees the first three prompts and the last two exchanges, never the middle, so a long conversation with a detour reads as what it started as and how it ended.
