# 07: A WezTerm window opened from the Plasma launcher puts its sessions under OOMPolicy=stop

**What to build:** not decided yet. Like 06, this is a problem write-up for the owner to triage. The fix touches how the owner opens their terminal, so the choice is theirs. Once it is decided, this ticket becomes the build.

**The problem:** the one WezTerm window running since the 2026-11-05 login was opened from the Plasma panel or menu, not by agentview. Plasma runs it in its own app unit, and that unit has `OOMPolicy=stop`. The window holds 4 `claude` processes. If the OOM killer kills any one process in that unit, systemd stops the whole unit and kills the window and all 4 sessions. This is how the restore failed on 2026-09-28 (ticket 06, Evidence: 151 processes killed after one OOM kill in the autostart unit). The login restore did not open a window of its own: it found this one running and reused it, as `snapshot.py` does when a window is already up. Sessions that the restore or a reopen adds as tabs in this window end up in the same unit.

**Blocked by:** None

**Status:** needs-triage

## Evidence

From ticket 06, "Cgroup check, 2026-11-10" (read-only, Sinead), and checked again read-only on 2026-11-11.

- **The window.** One `wezterm-gui`, pid 22119, started 2026-11-05 16:02:24. Its cgroup is `app-org.wezfurlong.wezterm@3004c8e51b5349fc8eb3766be6d8ac4a.service`, the unit Plasma creates for an app started from its launcher. On 2026-11-10: `KillMode=control-group`, `OOMPolicy=stop`, 733 tasks, 9.07 GB. On 2026-11-11: still active, `OOMPolicy=stop`, `KillMode=control-group`, 722 tasks.
- **Who opened it.** Its environment has `SYSTEMD_EXEC_PID=8124` and a `DESKTOP_STARTUP_ID` ending in `8124_…`, and pid 8124 is `plasmashell`. The journal has no `agentview: wezterm window` scope on 2026-11-05. It does have one on every other restore day since the scope change, except 2026-10-13. `~/.config/autostart` has no WezTerm entry, and `ksmserverrc` has `loginMode=emptySession`, so Plasma did not restore the window on its own. The window was opened by hand 16 seconds after the login restore started (`16:02:08 Started run-p8509-i25065.scope - agentview: tmux server`). The restore reused it and reported `resumed 22 session(s)` at 16:03:10.
- **What is exposed.** Of the 43 `claude` processes on 2026-11-10, 39 ran in `tmux-spawn-<uuid>.scope` units under the scoped tmux server (pid 8512, `agentview: tmux server`, `OOMPolicy=continue`). The other 4 ran in the Plasma WezTerm unit. On 2026-11-11 the WezTerm unit still held 4 `claude` processes.
- **Not the drop-in.** Ticket 06 concludes that `agentview.service`'s `switchover.conf` can go. That conclusion holds, because this window is outside the service either way.

## Ways out named so far

Ticket 06's conclusion names two. Neither has been tried.

- Restart the window once through the restore, so that it lands in an `agentview: wezterm window` scope with `OOMPolicy=continue`. This fixes today's window but not the next time one is opened from the launcher.
- Make a WezTerm window started from the launcher land in the same kind of scope, for example a launcher entry that goes through agentview, or a drop-in for the Plasma app unit that sets `OOMPolicy=continue`. Which of these, if any, is the owner's call.

### Option 1: a drop-in for the Plasma app unit

- **Version.** `systemctl --user --version`: systemd 259 (259.9-0ubuntu0.1).
- **Search path.** `man systemd.unit` on this machine: for an instance unit systemd reads the instance directory (`foo@bar.service.d/`), then the template directory (`foo@.service.d/`), then, for names with dashes, the prefix directories (`foo-.service.d/`). For this unit the candidates are `app-org.wezfurlong.wezterm@3004c8e51b5349fc8eb3766be6d8ac4a.service.d/`, `app-org.wezfurlong.wezterm@.service.d/` and `app-.service.d/`, in `~/.config/systemd/user/`. The man page says nothing different for transient units: a transient unit is a unit with a generated fragment, and the drop-in lookup is by name. Precedent on this machine: `/usr/lib/systemd/system/user-.slice.d/` ships a drop-in for slices that logind creates on the fly.
- **Live unit.** `DropInPaths=` is empty because no such file exists. `systemctl --user show -p DropInPaths` lists only files that exist, so it cannot show the candidate directories.
- **Not tested**, because the test is to create the file. What the documentation says: `OOMPolicy=` is read from the loaded unit, so after a `daemon-reload` the running unit would use the drop-in's value on its next OOM event, i.e. **the running window too**, without restarting it. That is the claim to verify first, on a throwaway unit, before relying on it. `systemctl --user set-property` does not help here: the man page limits it to properties that can change at runtime, and `OOMPolicy=` is documented as a unit-file setting.
- **Catch 1, the name form varies.** Plasma started WezTerm as `app-…@<id>.service`, but on this machine other apps are `app-…-<pid>.scope` (`app-com.google.Chrome-65918.scope`, `app-discord-1105097.scope`) and the same app appears in both forms (`app-com.google.Chrome@….service` and `app-com.google.Chrome-65918.scope`). A drop-in for `@.service.d` does not cover a scope-form launch; that would need `app-org.wezfurlong.wezterm-.scope.d`.
- **Catch 2, scope.** `app-.service.d` would cover every Plasma-launched app; the narrower `app-org.wezfurlong.wezterm@.service.d` only WezTerm.
- **Cost.** Two files and a `daemon-reload`, no change to agentview. It is a system-level setting on Thierry's session, outside the repo, so it would be documented in the README, not shipped.

### Option 2: a launcher entry that goes through agentview

- **What agentview already does.** `scope.wrap(argv, "wezterm window")` puts `systemd-run --user --scope --quiet --collect -p OOMPolicy=continue --description="agentview: wezterm window" --` in front of the command (`scope.py`, `SYSTEMD_RUN`). `snapshot._start_gui` (restore) and `jump.open_tab` (closed list, only when no `wezterm-gui` is running) both use it. With a window already up, both ask it by `wezterm cli spawn` instead, so the new tab lives in the window's cgroup. That is how the restore reused the Plasma window on 2026-11-05.
- **What the override needs.** The launcher entry is `/usr/share/applications/org.wezfurlong.wezterm.desktop`, `Exec=wezterm start --cwd .`; no override exists in `~/.local/share/applications/`. A file of the same name there wins. Its `Exec=` has to start the window through a scope: either the same command line (`systemd-run --user --scope --quiet --collect -p OOMPolicy=continue --description='agentview: wezterm window' -- wezterm start --cwd .`), which needs no agentview code at all, or a small `python3 -c 'import scope, subprocess; …'` wrapper that calls `scope.wrap` and gets its fail-open and `AGENTVIEW_SCOPE=off`. Plasma still creates its `app-…` unit for the launcher process; `systemd-run --scope` moves itself and the window out of it, which is the trick `scope.py` documents, so the Plasma unit ends once it is empty (`ExitType=cgroup`). Not tested.
- **Limits.** Covers only launches from that entry: a `wezterm` typed in a terminal, a KRunner hit on another entry, and a WezTerm started by something else are not covered. It does not touch today's window. An override of a package file is a copy that goes stale when the package changes it (here: a 12-line file).
- **Cost.** One file in the home directory, no daemon-reload. If the choice is to ship it, `scripts/` could install it and the README say so.

### Option 3: move today's window once through the restore

- **What goes.** Closing the Plasma window ends the whole unit (`KillMode=control-group`): the 1 direct `claude` and its children, the 6 `tmux attach` clients, `xbindkeys` (restart it by hand or at the next login), and the plain shells. The 31 `claude` processes under tmux are not in the unit and keep running.
- **What comes back.** `snapshot.py restore` reads the newest snapshot (the timer writes one every 2 minutes; `~/.claude/agentview/snapshots/`). It re-attaches the tmux tabs, resumes the one `claude` with `claude --resume <id>` as a WezTerm tab, and starts the window itself through `_start_gui`, so it lands in an `agentview: wezterm window` scope with `OOMPolicy=continue`. The plain shells come back as empty shells in their directories, without their history or what was running in them. The `claude` that was in flight loses its running turn.
- **What it costs.** 1 session interrupted (resumed, not lost), 8 tabs reopened, one shell history each. About a minute. It must be run when nothing is mid-turn in that `claude`, and it needs Thierry at the screen: it closes the window he is looking at.
- **Limit.** It fixes today's window only. The next launch from the Plasma panel puts the next window back in the same position.

### Recommendation

1. **Option 2 now** (the launcher override), because it fixes the cause for every window opened from the launcher and needs one file and no daemon-reload.
2. **Option 3 when the one direct `claude` is idle**, to move today's window into a scope; after option 2, nothing starts one outside a scope again.
3. **Option 1 only if the running window must be saved without closing it**, and only after a throwaway-unit test that the drop-in applies to the running unit. It is the only option that might reach the live window without closing it, and the only one whose key claim is untested.

Whichever is chosen, the README note under "Restarting the service" (a window opened from the launcher shows the launcher's own unit) stays true until option 2 or 3 is done.
